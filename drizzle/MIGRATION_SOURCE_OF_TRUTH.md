# Source de vérité des migrations Drizzle

La base de production est **PostgreSQL (Neon)**. La configuration active de Drizzle, `drizzle.config.ts`, déclare `dialect: "postgresql"` et `out: "./drizzle/pg"`. Les fichiers SQL et le journal (`meta/_journal.json`) présents sous `drizzle/pg/` constituent donc la seule source de vérité des migrations de ce projet.

## Contenu des dossiers

| Dossier | Statut | Rôle |
|---|---|---|
| `drizzle/schema.ts` | actif | Schéma TypeScript lu par le code et par drizzle-kit. |
| `drizzle/pg/` | **actif, source de vérité** | Migrations PostgreSQL. `0000_baseline.sql` recrée l'intégralité du schéma (36 tables) à partir de `drizzle/schema.ts`, générée par `drizzle-kit generate` (audit de lancement M32, 2026-10). Les migrations suivantes s'y ajoutent : `0001_appointment_invoices.sql` (factures numérotées, B3) est idempotente (`IF NOT EXISTS`), car l'application crée aussi cette table à l'exécution (`server/invoiceNumbering.ts`) ; elle vérifie d'abord ce qui existe et n'envoie aucune DDL quand la table et ses index sont déjà là, donc le rôle de `DATABASE_URL` n'a pas besoin d'en être propriétaire si 0001 a été appliquée avec un autre rôle (il lui faut alors `SELECT, INSERT` sur la table et `USAGE` sur sa séquence). `0002_language_columns.sql` (EN-01, EN-02) ajoute la colonne `language` (`varchar(10)`, `'fr'` par défaut, non nulle) à `appointments`, `cv_applications` et `candidate_accounts` ; elle est idempotente (`ADD COLUMN IF NOT EXISTS`) car l'application ajoute aussi ces colonnes à l'exécution, avec la même DDL, une fois par instance, à la première requête qui lit ou écrit cette colonne, c'est-à-dire qui nomme `language` et l'une de ces trois tables (`server/languageColumns.ts`, branché par `getDb()` sur le client Neon) : seules ces requêtes l'attendent, les autres (disponibilités et créneaux réservés, santé, questions médicales…) partent aussitôt. La vérification lit le catalogue (`to_regclass`, `pg_attribute`) sans verrouiller les tables, et rien n'est envoyé quand les trois colonnes existent. **Voie normale : appliquer 0002 avant de déployer le code qui lit ces colonnes.** L'ajout à l'exécution n'est qu'un filet de secours : il exige que le rôle de `DATABASE_URL` puisse modifier ces tables (en être propriétaire), et `ALTER TABLE … ADD COLUMN` prend un verrou exclusif sur la table. Son attente est bornée à 2 s (`SET LOCAL lock_timeout` dans le même bloc `DO`, neon-http n'ayant pas de transaction interactive) ; pendant ces 2 s au plus, il bloque aussi les lectures de la table par les autres sessions. Un verrou pris sur l'une des tables n'empêche pas d'ajouter la colonne aux deux autres. Un échec (verrou non obtenu, code 55P03, ou droits insuffisants, code 42501) est journalisé une fois par code (`[Database] Language columns check failed`, suivi du code ; le même échec répété ensuite reste silencieux jusqu'au retour à la normale), le retour à la normale une fois (`[Database] Language columns check succeeded after a failure`), et la vérification est réessayée par la première requête concernée 5 s après le premier échec, avec la même attente bornée à 2 s. Si ce nouvel essai attend encore le verrou sur l'une des tables (55P03), même si une autre échoue autrement, le verrou dure : chaque essai suivant n'a lieu qu'une minute après l'échec précédent, tant que les échecs se suivent. Les autres échecs (droits insuffisants, réseau), qui n'attendent pas le verrou et ne retiennent donc pas les lectures, doublent le délai (10, 20, 40 s) jusqu'à une minute au plus. Sous un verrou qui dure, les lectures de la table sont donc retenues jusqu'à 2 s au premier essai, puis au deuxième, environ 7 s après le début du premier, puis une fois par minute au plus et par instance (au plus 3 fois dans les 100 premières secondes) ; d'ici là, les requêtes qui lisent ou écrivent la colonne d'une table qui ne l'a pas encore échouent aussitôt au lieu d'attendre (quelques secondes après la fin d'un verrou bref, une minute au plus après un verrou long), le reste du site fonctionne. `0003_mission_shortlist_columns.sql` (IA-02, RGPD-03) ajoute `confirmed_at` à `cv_candidate_certifications` (certification confirmée par l'admin) et `candidate_consent_at` à `client_brief_candidates` (date de l'accord du candidat pour une mission), deux `timestamp` nullables sans valeur par défaut ; elle est idempotente pour la même raison : le même mécanisme (`RUNTIME_COLUMNS` dans `server/languageColumns.ts`, une colonne par table) les ajoute à l'exécution, à la première requête qui nomme l'une de ces colonnes et sa table, avec la même vérification unique du catalogue pour les cinq colonnes, la même attente bornée, les mêmes délais avant un nouvel essai et les mêmes journaux (`Language columns check…`). **Voie normale : appliquer 0003 avant de déployer le code qui lit ces colonnes.** |
| `drizzle/legacy-mysql/` | **historique, en lecture seule** | Anciennes migrations MySQL/TiDB de l'époque Manus (`0000`–`0027`, journal `dialect: mysql`) et ancien dossier manuel `drizzle/migrations/` (déplacé dans `drizzle/legacy-mysql/manual/`). Aucune instruction ne s'applique à PostgreSQL : ne jamais les exécuter, ne rien y ajouter. Conservées uniquement pour la traçabilité. |

Vérifié sur une base PostgreSQL 16 vierge (réplique locale de l'audit) : le migrateur `drizzle-orm/neon-http` applique `drizzle/pg` sans erreur, produit 36 tables, 468 colonnes et 95 index identiques au schéma attendu par le code, et une seconde exécution ne fait rien (journal `drizzle.__drizzle_migrations`).

## Procédure obligatoire pour toute évolution du schéma

1. Modifier le schéma TypeScript dans `drizzle/schema.ts`.
2. Générer la migration incrémentale : `pnpm db:generate` (alias de `drizzle-kit generate`, aucune base requise ; `--name=<objet>` pour nommer le fichier). Elle est écrite dans `drizzle/pg/`, avec l'instantané `meta/NNNN_snapshot.json` du nouveau schéma et son entrée dans `meta/_journal.json`.
3. Lire intégralement le SQL produit et vérifier son ordre, ses index et sa réversibilité métier. Préférer des instructions idempotentes (`ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`) lorsque le code crée aussi la colonne à l'exécution : on réécrit alors le `.sql` généré (c'est ainsi qu'ont été écrites 0002 et 0003), jamais l'instantané ni le journal.
4. Appliquer le SQL explicitement avec l'outil de migration de la plateforme, puis comparer les tables et colonnes réellement déployées.
5. Ajouter ou mettre à jour les tests couvrant le contrat modifié. Le test `server/migrationSourceOfTruth.test.ts` échoue tant que `drizzle/pg` ne couvre pas toutes les tables et colonnes de `drizzle/schema.ts`.
6. Vérifier que le schéma et les migrations concordent : `node scripts/check-migrations-in-sync.mjs` (voir ci-dessous).

Ne jamais employer `drizzle-kit push` (ni l'ancien `pnpm db:push`) comme raccourci non revu en production.

## Contrôle de la CI : schéma et migrations synchrones

Après le build, le job *quality* de `.github/workflows/ci.yml` lance `node scripts/check-migrations-in-sync.mjs`, qui exécute `drizzle-kit generate` avec `drizzle.config.ts` et exige sa réponse « No schema changes, nothing to migrate » ; `git diff --exit-code -- drizzle/pg` puis l'absence de fichier non suivi dans `drizzle/pg` confirment qu'il n'a rien écrit. Le message est exigé parce que drizzle-kit répond 0 même quand il échoue sans rien écrire (schéma qui ne se charge pas, instantanés en collision, renommage qui attend une réponse au clavier). En local, la même commande écrit dans `drizzle/pg` la migration manquante s'il y en a une : la relire et la garder, ou la supprimer avec son instantané et son entrée de journal. `server/migrationsInSync.test.ts` fait la même vérification sur une copie de `drizzle/pg`, dès `pnpm test:ci`.

Pour ajouter une migration sans casser ce contrôle :

- Toujours partir de `pnpm db:generate` (étape 2). Une migration écrite entièrement à la main (SQL et entrée de journal) laisse l'instantané sur l'ancien schéma : `drizzle-kit generate` produirait de nouveau la même modification et la CI échouerait.
- `pnpm db:generate --custom --name=<objet>` crée un fichier vide dont l'instantané recopie le précédent : à réserver au SQL qui ne change pas le schéma (données, droits).
- Deux branches qui ajoutent chacune une migration (par exemple deux `0004`) se heurtent à la fusion (`meta/_journal.json`, `meta/0004_snapshot.json`), et leurs instantanés désignent le même parent : renuméroter à la main ne suffit pas, drizzle-kit refuse la « collision ». La branche fusionnée en second supprime sa migration (le `.sql`, son instantané et son entrée de journal), refait `pnpm db:generate` sur la branche principale à jour (sa migration devient `0005`), y reporte ses retouches manuelles du SQL, puis relance `node scripts/check-migrations-in-sync.mjs`.

## Utilisation de la baseline

- **Nouvel environnement ou reprise après sinistre** : sur une base PostgreSQL **vide**, `DATABASE_URL=<base vide> pnpm drizzle-kit migrate` recrée tout le schéma.
- **Production existante** : la baseline ne doit **pas** y être rejouée (les tables existent déjà ; `CREATE TABLE` échouerait sans rien modifier). Aucune action n'est requise pour le lancement. Si le propriétaire souhaite ensuite appliquer les migrations incrémentales avec `drizzle-kit migrate`, il faudra d'abord, après sauvegarde et comparaison du schéma réel (export `information_schema.columns`), marquer la baseline comme appliquée dans `drizzle.__drizzle_migrations`.

Cette règle prévient les divergences silencieuses entre le schéma TypeScript, les fichiers versionnés et la base de production.
